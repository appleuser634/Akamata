## このラウンドで試したこと

### 1. 直接ストリーミング書き込み (中間アリーナバッファーなし)

変更: `serve.zig` で、置き換えます

```zig
var alloc_w: Io.Writer.Allocating = .init(arena);
try res.writeTo(&alloc_w.writer);
const out = alloc_w.writer.buffered();
w.writeAll(out); w.flush();
```

`res.writeTo(w)` をソケットバッファーライターに直接入力します。

仮説: アリーナを通じて 1 つの完全な応答コピーを保存します。

**4 KB ソケット バッファでの結果:** `/echo` は最大 14 % 低下しました。
マルチヘッダーの `w.print()` 呼び出しによりバッファがオーバーフローし、追加の呼び出しがトリガーされました
`send()` システムコール。

**16 KB ソケット バッファでの結果:** `/echo` は ~174 k まで回復しましたが、
`/hello`は169kまで下がりました。ネット洗浄、測定ノイズ以内。

**評決: アリーナバッファ + シングルショット writeAll パターンを維持しました。**
最終的な TLS / プロキシの場合にも優れています (1 つの連続したペイロード)
応答ごとに）。

## 候補者はまだ挑戦していません

推定労力 × 影響度で並べ替えられます。

### より少ない労力で勝利 (それぞれ 1 ～ 2 日)

|アイデア |期待される利益 |リスク |
|---|---|---|
| `memchr` ベースのヘッダー パーサー (名前ごとの `std.mem.indexOf` の代わり) | `/hello` で +5-10% |低い |
|接続ごとに事前にサイズ設定されたアリーナ (最初の 16 KB realloc をスキップ) | +2-5% |低い |
|既知のフィールド (`content-length`、`connection`) の線形ヘッダー テーブルをスキップします。小さなインライン配列を介してキャッシュします。 +1-3% |低い |
|ステータス行の事前計算テーブル (リクエストごとの `phrase()` ルックアップを回避) | +1% |低い |
| `cpu_count()` からの `accept_thread_count` 自動調整 |変数;プロビジョニング不足のデフォルトを支援します。低い |

### 中間作業 (3 ～ 5 日)

|アイデア |期待される利益 |リスク |
|---|---|---|
|受け入れループごとに 1 つのスレッドの代わりに Reactor + readiness (kqueue/epoll) | `/hello` では +20 ～ 30 %; Go の差のほとんどを埋める |高 — スレッドモデルを変更します。応力マトリックスの完全な再テストが必要 |
| `SO_REUSEPORT` なので、各受け入れスレッドには独自のリスナーがあります。 +5-15% |中 - Linux と macOS の現在の動作とは異なります |
| HTTP/2 (OpenSSL 経由の TLS 経由) |多重化されたクライアントではスループットが向上しますが、wrk では**そうではありません**。高 |
| Linux 上の `io_uring` | Linux ではおそらく +10 ～ 20 % |中 — macOS を現在のパスに維持します。

### 大規模な調査

- **リクエストごとのアリーナ アロケーター監査。** プロファイルは、`arena.alloc` が
  システムコール以外の主なコスト。メタデータのないカスタム バンプ アロケータ
  オーバーヘッドにより意味のあるスライスが削られてしまいます。
- **応答構造体プーリング。** 現在、`Response.init` はゼロ + サイズを設定しています。
  リクエストごとに `ArrayList`。事前に割り当てられた応答のスレッドローカル プール
  オブジェクト (取得時クリア) はそれを償却します。
- **JSON シリアル化の書き換え。** `std.json.Stringify.value` は現在
  `/echo` で最大の CPU コスト。以下から生成されるスキーマ認識エミッタ
  コンプタイム時の応答タイプは 2 ～ 3 倍も優れています。

## 再現方法

```bash
zig build -Dexample=bench -Doptimize=ReleaseFast
./zig-out/bin/bench &

# /hello
wrk -t8 -c256 -d10s --latency http://127.0.0.1:8080/hello

# /echo
cat > /tmp/wrk_echo.lua <<'LUA'
wrk.method = "POST"
wrk.body   = '{"name":"x","n":42}'
wrk.headers["content-type"] = "application/json"
LUA
wrk -t8 -c256 -d10s --latency -s /tmp/wrk_echo.lua http://127.0.0.1:8080/echo

# /db (round-robins ids 1-3)
cat > /tmp/wrk_db.lua <<'LUA'
math.randomseed(os.time())
request = function() return wrk.format("GET", "/db/" .. tostring(math.random(1,3))) end
LUA
wrk -t8 -c256 -d10s --latency -s /tmp/wrk_db.lua http://127.0.0.1:8080
```

より長い/より多くの敵対的実行については、`docs/ja/benchmarks-long-run.md` を参照してください。

## 方法論のメモ (将来の数値を比較できるようにするため)

1. **macOS の結果には、実行ごとに ±3 ～ 5 % のジッターが発生します。** の中央値を取得します。
   30 秒のウォームアップの後、結論を出す前に 10 秒のランを 3 回実行します。
2. **ループバック測定値はシステムコール コストをアンダーカウントします** (実際の NIC はありません)。あ
   10 Gbps NIC 上の実際の Linux ボックスでは、異なる相対ギャップが見られます。
3. **wrk は *発行された*リクエスト数を報告します。** 常にクロスチェックしてください。
   `Non-2xx or 3xx responses` — ゼロ以外は、ベンチマークを行っていないことを意味します
   私たちはそうだと思います。
4. **10 秒間隔で RSS サンプリングを行うだけで十分です。** リークは次のように表示されます。
   直線的な成長。一時的なスパイクは 1 つのサンプリング ウィンドウ内で安定します。
